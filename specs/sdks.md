# SDKs

The design of record for non-Rust implementations.

## The split

An SDK is **generated types on a hand-written runtime**. Never a hand-rolled
JSON-RPC loop per protocol per language.

| Half | Written | Contains |
|------|---------|----------|
| runtime | once per language, by hand | framing, classification, serve loop, dispatch, handshake, version negotiation |
| protocol | generated by `lanok gen` | payload types, method names, capability tokens, direction table |

The runtime half is the hard part and is identical for every protocol. Getting
it right once per language is the entire argument for this kit. The generated
half is genuinely per-protocol and entirely mechanical, so no human writes it.

## Layout

```
sdks/python/lanok/        the runtime: _wire.py, _version.py, _server.py
sdks/python/tests/        mirrors the Rust suite case for case
sdks/typescript/src/      the runtime: wire.ts, version.ts, server.ts
sdks/typescript/tests/    mirrors the Rust suite case for case
```

Generated protocol modules sit alongside the runtime (`_generated_<name>.py`,
`generated<Name>.ts`) and are committed, so a consumer needs no build step and a
diff shows a wire change.

## Parity is enforced, not assumed

Two mechanisms, and both must stay:

1. **The test suites mirror each other case for case.** A divergence in framing
   shows up as a failure in one language and not the others.
2. **One conformance suite runs against every implementation.** The same
   vectors that check the Rust server check the Python and TypeScript ones, in
   CI. This is what makes "first-class" a fact rather than a claim.

When adding a rule to the wire, add it to all three suites in the same change.

## What the runtimes deliberately do not have

- **No client peer.** The SDKs serve; they do not drive. Hosts are Rust today,
  and a half-finished client in two more languages is worse than none.
- **No concurrency.** Both SDK servers are serial, matching `SimpleServer`.
  This is stated in their READMEs rather than discovered, and it means neither
  can serve a reverse request.

Both are scope decisions, not oversights. Revisit them when there is a consumer,
not before.

## Type generation

`lanok gen` covers the shapes a protocol payload actually uses: objects with
named properties, arrays, primitives, `$ref`, enums, and unions with null.
Anything outside that becomes `Any` / `unknown` rather than failing generation,
so an exotic payload costs precision rather than a usable SDK.

Optionality comes from JSON Schema's `required`, which is what `#[serde(default)]`
produces, so an optional Rust field is an optional SDK field without anyone
restating it.

## Drift

`lanok gen --check` fails when a committed file is not what would be generated.
It runs in CI for both languages. A protocol change that does not regenerate its
SDKs fails the build rather than shipping a mismatch.

## Publishing

| Language | Package | Notes |
|----------|---------|-------|
| Python | `lanok` on PyPI | `requires-python >= 3.11` for `NotRequired` |
| TypeScript | `@lanok/rpc` on npm | ESM only, Node 20+ |

Versions track the Rust crates, because the wire contract they implement is the
same one. A runtime change that is not a wire change still bumps with the rest:
one version number for one contract is worth more than precise independence.
